The strongest finding is that the page can report a chunk complete before its delayed picture has finished. The reported −45 ms model offset also needs remeasurement before it supports the “no server-side shift” conclusion.

1. **High — `chunk_end` can contain incomplete `painted` evidence.** In [index.html:render](/data/zhoutaichang/live-agent/live_agent/server/static/index.html:724), the queue retains a chunk after its audio `onended` acknowledgment, but that acknowledgment has already sent `painted`. At a +200 ms picture offset and an 80 ms audio output delay, the picture can be roughly 260 ms—about six 24 fps frames—short of the end when audio `onended` fires. Later draws never update the server’s evidence. Background-tab rAF pauses make the gap larger. **Fix:** track audio completion and picture completion separately; send final `painted` evidence when the picture reaches the end, and distinguish cancellation from completion.

2. **High — the lip-sync estimator introduces edge signals into every speech run.** [tools/av_sync.py:`_highpass`](/data/zhoutaichang/live-agent/tools/av_sync.py) convolves each run with zero padding. A steady positive `jawOpen` value produces positive spikes at both edges; a steady negative dB level produces negative spikes. For a minimum two-second run, the one-second filter affects about half the samples. With reported peak correlations of only 0.118 and 0.094, those artifacts could materially affect the chosen lag. **Fix:** remove each run’s baseline before filtering, use reflected or valid-window filtering, trim affected edges, and rerun the recordings.

3. **Medium — the CI and absolute offset claim are stronger than the method supports.** [tools/av_sync.py:`measure`](/data/zhoutaichang/live-agent/tools/av_sync.py) finds the global peak, then forces every bootstrap replicate to search within ±3 frames of that selected peak. Its interval therefore excludes replicates whose global peak moves to another lobe; it is not a 95% interval for the reported unrestricted estimator. `jawOpen` versus sound level also measures an articulation rhythm, whose natural phase need not be zero. The ±frame self-checks confirm shift direction, not the absolute zero point. **Fix:** report unrestricted bootstrap peaks and competing-lobe frequencies, then validate the absolute estimate on known-synchronous speech and independently judged clips before treating “no server-side shift” as measured.

4. **Medium — changing the offset can strand the needed frame.** [index.html:render](/data/zhoutaichang/live-agent/live_agent/server/static/index.html:724) removes a chunk once `t >= end`. Suppose it has just been removed and the viewer moves “画面延后” from 0 to +300 ms: `mediaTime()` jumps back into that removed chunk. No queued chunk is eligible, so the canvas holds a frame from the future until the clock catches up. **Fix:** retain enough picture history for the full offset range and redraw immediately after a slider change, or apply offset changes at a controlled chunk boundary. The same filter needs explicit cleanup if `stopAll` suspends the audio clock; whether `stopAll` already clears the queue is not shown.

5. **Medium — one-refresh display compensation is an unverified physical delay.** [index.html:`mediaTime`](/data/zhoutaichang/live-agent/live_agent/server/static/index.html:655) adds a full measured rAF interval. An rAF callback runs *before* the next repaint; that does not establish that its canvas update reaches the viewer exactly one full interval later. It may advance the selected frame by nearly a refresh on one display and undercompensate on another. Positive `avOffsetMs` does have the intended sign: it reduces media time and delays the picture. **Fix:** predict the actual presentation instant in the `performanceTime` clock and validate flash-to-sound timing on representative displays. The [`getOutputTimestamp()` specification](https://www.w3.org/TR/webaudio-1.1/) defines its two values as a paired clock observation; [rAF timing](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame) alone does not supply photon time.

6. **Medium — the audio-clock fallback omits a latency stage.** [index.html:`heardTime`](/data/zhoutaichang/live-agent/live_agent/server/static/index.html:646) falls back to `currentTime - (outputLatency || baseLatency || 0)`. Where both values exist, `||` subtracts only one, although [the Web Audio specification](https://www.w3.org/TR/webaudio-1.1/) describes separate processing and output-device latencies. A browser that takes this fallback can show the lips early. **Fix:** use a documented combined estimate for that browser, and test the fallback with both values nonzero. The supplied excerpt omits the main `getOutputTimestamp()` branch, so its `contextTime`/`performanceTime` calculation cannot be verified here.

7. **Medium — the page check can pass with the wrong audible clock.** [scripts/lipsync_page_check.py:`playback` and `calibration`](/data/zhoutaichang/live-agent/scripts/lipsync_page_check.py) compare page values against formulas built from those same values. A consistently wrong `heardTime()` can still produce zero `wrong_index` and the expected `media_minus_heard_ms`; the flash hook likewise records the page’s own `heardTime`, not an observed flash or beep. `painted` records canvas draw calls, not frames confirmed on screen. **Fix:** inject known `contextTime`/`performanceTime` pairs for a clock unit test, exercise hidden-tab, offset-change, stop, and reconnect transitions, and use an external audio/video capture for physical alignment. The [synthetic media tests](/data/zhoutaichang/live-agent/tests/test_av_alignment.py) verify useful recording and PCM properties, but use four 34-frame chunks rather than the 34/34/34/17 ending and do not test browser scheduling or acknowledgments.

8. **Low — calibration can give a confusing result during live playback.** [index.html:`avTest`](/data/zhoutaichang/live-agent/live_agent/server/static/index.html:675) allows repeated clicks while earlier oscillators remain scheduled, and allows beeps over a live lesson. If push-to-talk ducks `outGain()`, it can duck the beeps too. **Fix:** cancel a previous calibration before starting another, and run calibration only in a quiet, known-gain playback state. A saved +200 ms offset should also be reconsidered when the viewer switches from Bluetooth headphones to speakers.

Under the stated contiguous `start`/`end` schedule, I do **not** see evidence that the queue filter itself draws an older chunk over a newer one: only one chunk should be eligible at a given `t`. The reproducible stale-picture case is the offset change in finding 4. The omitted `stopAll`, reconnect, and `onended` bodies prevent a definitive audit of their cleanup behavior.
